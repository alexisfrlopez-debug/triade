LISEZMOI-RUN-UNITE02-D210-1CLIC — LE RUN DE L'UNITÉ 01 D210 EN UN CLIC
(l'édition v1.0.0 du 18/11/2026 ; la commande du développeur : « fais un
GUI 1 clic autonome pour ce test » — LE KIT ET LE GUI EN UN SEUL DOSSIER,
une pièce de plus à installer qu'un Python ; le GUI de campagne v1.0.1
demeure au coffre, INTACT — D143 : jamais jeté)
================================================================================

L'OBJET : conduire LE GESTE TERRAIN de la première unité de la campagne
D210 (loupe-02 lire × bras T — le LISEZMOI-KIT-UNITE-01-D210 du kit fait
foi : l'ordre de jeu 1·KIT → 2·RUN → 3·TÉMOIN) SANS AUCUN CHOIX DE
DOSSIER : le kit VIT DANS CE DOSSIER (loupe.exe, le scénario scellé, les
témoins, les gravures), le GUI le recoupe LUI-MÊME à chaque lancement.

LE GESTE : dézippez ce kit où vous voulez (Téléchargements, Bureau) —
kit-gui-1clic-unite02-d210-20261118/ — puis DOUBLE-CLIQUEZ
LANCER-RUN-UNITE02-D210-1CLIC.bat. La fenêtre s'ouvre sur LE VERROU
(l'étape 1 se recoupe seule) ; si un cadre « Windows a protégé votre PC »
apparaît : clic droit sur le .bat, Propriétés, cochez « Débloquer », OK —
la marque du web, comme toute pièce téléchargée du coffre.

LE CORRECTIF T0 QUE CE KIT PORTE (le 18/11, nommé au GUI et prouvé à
chaque lancement) : le kit kit-unite-01-d210-20261117 tel que livré portait
EMPREINTES-KIT-UNITE-01-D210.txt au format « nom  taille o  sha256 » —
le scénario scellé (scenario-unite02.py, b3e896f7…, D204 INCHANGÉ) lit les
gravures « sha256  nom » : il y voyait ZÉRO pièce, T0 aurait REFUSÉ
(« aucune EMPREINTES*.txt au kit — rien ne court »). CE kit porte la
gravure ADDITIONNELLE EMPREINTES-PIECES-RUN.txt (les QUINZE pièces au
format parsé) ; l'EMPREINTES-KIT d'origine demeure INTACT à ses côtés
(D143). LA PREUVE T0 : le GUI extrait lire_empreintes DU FICHIER LIVRÉ
par AST et l'exécute sur ce dossier AVANT tout lancement — « le scénario
scellé voit 15 pièces (loupe.exe recoupé cf251c12…) » s'affiche en vert ;
le moindre écart = le bouton reste gris, RIEN ne court.

LA FENÊTRE — LES CINQ ONGLETS :
  1·VERROU   — LES DIX-SEPT pièces recoupées sha256 par sha256 (les
               QUINZE du kit + les DEUX gravures) + LA PREUVE T0 ;
               une divergence, RIEN ne court (fail-closed) ;
  2·RUN      — LE BOUTON VERT « TOUT LANCER » : le scénario couru
               TEL QUEL, SA console écrite AU FIL DE L'EAU (chaque
               ligne couchée et flushée à mesure — un crash laisse la
               console VIVANTE), UTF-8 des deux côtés du tuyau
               (PYTHONIOENCODING posé par le GUI), la console sauvée à
               run-console-unite02-d210-<horodatage>.txt ; les verdicts
               RECOPIÉS des lignes [VERT]/[ROUGE] (jamais recalculés) ;
               le chrono M4 (début/fin/durée mesurés) ; REJOUER conduit
               le rejeu diagnostic (le rejouage d'une unité verte n'est
               PAS une livraison, § 7) ;
  3·TÉMOIN   — LE VERROU D99 : le GUI ne signe JAMAIS. Le témoin naît
               DU SCÉNARIO (preuves-unite02/temoin-unite02.txt, aux
               blancs « Daté le : » / « Signé    : ») ; ouvre-le au
               bloc-notes, DATE et SIGNE de votre main, puis
               ASSEMBLER LE ZIP : preuves-unite02-d210-<UTC>.zip (le
               réceptacle ENTIER + le DEPOT + la console) — l'assemblage
               EXIGE le témoin daté-signé (refus nommé sinon) et REFUSE
               au-delà de la cap M1 (TROIS livraisons par bloc, la règle
               § 7 du plan D204) ; renvoyez le zip au coffre /test (le
               bouton OUVRIR LE COFFRE y mène au navigateur — le GUI
               n'écrit JAMAIS au Drive) ;
  4·LIVRE    — les lignes AU GESTE : la ligne de carnet M3
               (T-loupe-02-d210-it1), la ligne de livraison M1
               (livraisons.csv), LA RÈGLE D202 (les défauts nommés AVANT
               correction, defauts.csv), le chrono M4 (le labo mesura :
               build 0,5 s ; oracle V1-V5 33,6 s — le terrain mesure au
               geste présent) ; le livre se remplit À LA MAIN au
               bloc-notes, jamais ici ;
  5·JOURNAL  — le journal de la session (chaque geste y vit) ; si un
               écran nomme un défaut, renvoyez TRIADE_logs/ TEL QUEL.

UN RUN ROUGE (le scénario rend 1) : le run FINIT quand même — le témoin
naît, le dossier de preuves se renvoie ENTIER (le dépôt d'un run rouge
est AUSSI un témoin) et LES DÉFAUTS SE NOMMENT AVANT CORRECTION (D202).
Un REFUS (le code 2 — une pièce divergente, une empreinte absente) : le
GUI s'arrête et NOMME la cause — ARRÊTEZ, ne modifiez AUCUN fichier, la
console vivante se renvoie TELLE QUELLE.

CE QUE CE GUI NE FERA JAMAIS (les frontières, tenues par construction) :
  — DATER ni SIGNER un témoin : votre main, toujours (D99) ;
  — DÉPOSER au coffre : il OUVRIRA le /test au navigateur, il n'écrit
    JAMAIS au Drive ;
  — FABRIQUER un chiffre : les verdicts sont RECOPIÉS des lignes de
    console ; le compte VERT/ROUGE est un recomptage des lignes
    couchées, jamais une réévaluation ;
  — TOUCHER les pièces scellées : le scénario, loupe.exe, les témoins
    LUS (le scénario lui-même recoupe loupe.exe AVANT de courir — le
    moindre écart = [T0] REFUS, RIEN ne court) ;
  — RENOMMER ni ÉDITER les pièces du réceptacle (le témoin, les
    consoles : COPIÉES, jamais retouchées) ;
  — DÉPASSER la cap M1 : TROIS livraisons par bloc — le quatrième zip
    refuse, le refus est NOMMÉ.

LA MÉMOIRE DU GUI : etat-run-unite02-d210.json (à côté du GUI) retient
les étapes vertes, le contexte du run (console, verdicts, chrono),
les livraisons assemblées — rouvrez le GUI, tout se retrouve (et si
l'état périt, il se RECOMPLÈTE des pièces nées : la console la plus
récente, le témoin — RELUS, jamais réinventés, la source nommée).
TRIADE_logs/ conserve le journal de chaque session.
