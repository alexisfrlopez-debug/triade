LISEZMOI — LE KIT-B DUDECT-ORACLE (le test du silicium serveur Ampere A1,
l'édition ORACLE ARM64 du troisième-silicium-étendu)
==============================================================================

LA COMMANDE (le développeur, 25/11/2026) : « si tu as des idées pour des
siliciums supplémentaires du même type que google collab (environnement
gratuit en ligne, mais hardware différent) ». LE SILICIUM AMPERE A1
(ARM64, coeurs Neoverse N1 à cadence fixe, cœurs DÉDIÉS) vit
gratuitement : l'offre Always Free d'Oracle Cloud en donne l'usage
(1 500 heures-OCPU et 9 000 Go-heures par mois — l'équivalent de
2 OCPU et 12 Go en continu pour un locataire Always Free, vérifié sur
la page d'Oracle le 25/11/2026 ; carte bancaire exigée à l'inscription
pour la vérification d'identité, sans prélèvement). C'EST le « hardware
différent » demandé : UN VRAI serveur ARM64, une AUTRE famille que le
Cortex du téléphone, une AUTRE que les Xeon/EPYC — et à la différence
de Colab/Kaggle, la machine est À VOUS seuls (pas de voisins de
session ; l'hôte physique demeure mutualisé, nommé ci-dessous).

L'ÉTAT DU KIT : NOUVEAU, PRÉPARÉ AU LABORATOIRE LE 25/11/2026, HORS DU
PÉRIMÈTRE SCELLÉ v0.15.0. LA PIÈCE EST LA MÊME : dudect_arm.c et
scenario-dudect-arm.py sont les pièces BYTE-POUR-BYTE du kit-B de
l'édition TÉLÉPHONE (Entrées 424/425 — le scellé de la source :
08681278e0efe013ff9e6379eff8ea02219f04a6bdbcb59b4a5d2a1016474a32).
SEUL LE PRÉSENT LISEZMOI ET LE LANCEUR SONT NEUFS. Le protocole
ORACLE-ARM-1 ci-dessous est PRÉ-ENREGISTRÉ AVANT tout run : l'équation
est l'ÉGALATION du TELEPHONE-ARM-1 (la pièce ne change pas, l'équation
ne change pas), re-enregistrée pour CE silicium serveur.

CE QUE CE KIT REFUSE (dit d'abord, pour qu'aucune déception ne naisse) :
  — les pièces scellées v0.15.0 (loupe.exe, proxy-image.bin,
    moteur-shani.bin) sont x86-64 Windows : CE silicium ARM64 ne les
    exécute PAS (l'ISA diverge, la convention d'appel diverge,
    sha256rnds2 n'existe pas ici). REFUSÉES PAR NATURE — leurs
    empreintes sont citées dans le binaire, jamais mesurées ici ;
  — les cibles VAES/AES-GCM de la campagne (P5) : c'est le couloir du
    PC x86-64, hors de ce kit ;
  — le moteur d'oracle et les 27 harnais par bloc : ils demandent le
    poste réel x86-64, pas ce silicium.

LE PROTOCOLE ORACLE-ARM-1 (l'équation pré-enregistrée, l'égalation du
TELEPHONE-ARM-1) :
  Les CIBLES, dans cet ordre :
    1. eq-constant     le CONTRÔLE POSITIF de l'instrument : la
                       comparaison de 32 octets par OU masqué — aucun
                       branchement sur le secret. ATTENDU : aucune
                       divergence au seuil. (Une divergence serait un
                       RÉSULTAT précieux : D189, consigner tel quel.)
    2. eq-branchue     le CONTRÔLE NÉGATIF : la sortie au premier octet
                       divergent — LE FAUX PATRON. ATTENDU : DIVERGENCE
                       — la preuve que l'instrument détecte les fuites.
                       Si elle ne diverge PAS : l'instrument est
                       CONTESTÉ sur cet échantillon, le verdict le
                       nomme (un instrument non éprouvé ne mesure rien).
    3. sha256-logiciel la compression SHA-256 logicielle d'un bloc de 64
                       octets (la même mécanique que la cible tls13-02
                       du kit-2 : l'état AMONT est l'IV, le bloc est LE
                       SECRET). ATTENDU : aucune divergence.
    4. sha256-arm-sha2 la compression par les INSTRUCTIONS MATÉRIELLES
                       FEAT_SHA256 (SHA256H/SHA256H2 — la famille
                       matériel ARM, UNE AUTRE que la SHA-NI x86 : les
                       deux mondes se constatent, aucun ne se déguise).
                       VIT SEULEMENT si le noyau expose le drapeau
                       « sha2 » aux Features de /proc/cpuinfo ET que le
                       compilateur a accepté -march=armv8-a+sha2 —
                       sinon REFUS NOMMÉ, le reste du run vit. ATTENDU :
                       aucune divergence. (L'Ampere A1 Neoverse N1 porte
                       FEAT_SHA256 — mais le kit n'affirme rien : le
                       drapeau du noyau décidera, nommé.)
  Les CLASSES, deux par cible, ÉCHANTILLONS ENTRELACÉS (à CHAQUE
  itération la première classe vit puis la seconde — les deux classes
  vivent les mêmes fenêtres thermiques ; c'est la différence nommée
  avec le kit-2, aux classes séquentielles) :
    — comparaisons : la classe EGAL (le secret est la copie de
      l'étalon — la comparaison court les 32 octets) contre la classe
      DIVERGENT (un secret frais — la sortie au premier octet
      divergent, presque sûr) ;
    — compressions : la classe SECRET-FIXE contre la classe
      SECRET-ALÉATOIRE (l'invariance de données).
  L'ÉQUATION : échauffement 100 paires par cible (résultats jetés) ;
  un échantillon mesure un LOT d'appels : LOT=512 pour les
  comparaisons, LOT=4 pour les compressions ; N échantillons par
  classe, N=60 puis N=200 puis N=400 DANS CET ORDRE (trois runs
  complets — l'ordre du LISEZMOI-KITS-TERRAIN) ; la statistique est le
  t de Welch sur les ticks, le seuil |t| > 5 (les mêmes paramètres que
  le kit-2, le kit-B et le kit-C).
  LE COMPTEUR : CNTVCT_EL0 sur aarch64 — le compteur virtuel du SoC,
  PAS le cycle CPU (sa fréquence varie selon le silicium : la grandeur
  est nommée « ticks », jamais « cycles ») ; si la lecture est refusée
  (SIGILL), le repli CLOCK_MONOTONIC est NOMMÉ, jamais muet.
  Contrepoint CLOCK_MONOTONIC en secondes (la colonne « secondes » du
  csv).
  L'ÉPREUVE PRÉALABLE : le condensé FIPS 180-4 « abc » EXACT exigé du
  lecteur logiciel ET du lecteur matériel (si présent) AVANT toute
  mesure — un lecteur faux est un REFUS : rien n'est mesuré.

LA MACHINE DE COMMODITÉ SE NOMME (D206) : la VM Ampere A1 du locataire

session comme au Colab/Kaggle) — MAIS l'hôte physique demeure mutualisé

pièces après le run). La hiérarchie d'évidence est INCHANGÉE : le banc
contrôlé (portable, téléphone) demeure la référence ; ce run est une
lecture de commodité, jamais une preuve.

LE RUN (sur la VM Ubuntu 22.04/24.04 ARM64 de l'offre Always Free —
voyez A-LIRE-EDITION-ORACLE.txt pour l'inscription, geste par geste) :
  1. téléversez le dossier du kit sur la VM (scp ou copier-coller via
     la console Cloud Shell) :
       scp -i <cle-ssh> TRIADE_kit_test_ORACLE_arm64_v100.zip ubuntu@<ip-vm>:~
       ssh -i <cle-ssh> ubuntu@<ip-vm>
       unzip -q TRIADE_kit_test_ORACLE_arm64_v100.zip
  2. tapez   bash TRIADE_kit_test_ORACLE_arm64_v100/COMMENCER-ICI.sh
     — le lanceur INSTALLE Python ET gcc TOUT SEUL s'ils manquent
     (apt-get), COMPILE la pièce sur cette machine depuis la source (la
     source est la vérité : aucun exe précompilé ne vit dans ce kit,
     rien ne peut être retiré par un antivirus), vit l'épreuve FIPS,
     puis les TROIS runs N=60, N=200, N=400 dans l'ordre imposé ;
  3. quelques minutes ; le réseau ne sert qu'à l'installation éventuelle
     des paquets ; aucun droit particulier (le compte « ubuntu »
     suffit, sudo n'est utilisé que pour apt-get).

LA LECTURE HONNÊTE (à lire AVANT de s'inquiéter d'un verdict) :
  — |t| > 5 = dépendance AU SEUIL sur CET échantillon, consignée telle
    quelle ;
  — |t| <= 5 = aucune divergence au seuil sur cet échantillon, CETTE
    machine — jamais « temps constant prouvé » ;
  — le contrôle négatif eq-branchue DOIT diverger (sinon l'instrument
    est CONTESTÉ — nommé) ;
  — le rapport médian logiciel/matériel (s'il vit) est LE CONSTAT DE CE
    SILICIUM — jamais une cible : aucune cible pré-enregistrée
    n'existe pour Ampere A1 (le téléphone a rendu 4,36 — CE silicium
    dira ce qu'il dit) ;
  — un écart nommé est un RÉSULTAT aussi précieux qu'un vert (D189) :
    rapportez-le tel quel.

LA PREUVE DU LABORATOIRE (ce que le labo a vécu AVANT de livrer) :
  la mécanique fut éprouvée de deux mains — l'autotest natif sur un
  hôte Linux x86-64 (gcc, TSC), où l'instrument s'était D'ABORD
  contesté lui-même (le contrôle négatif ne divergeait pas ; l'écart
  fut nommé, la structure des classes corrigée) ; PUIS la voie QEMU :
  la pièce croisée aarch64 (gcc, -march=armv8-a+sha2, statique) éprouvée
  sous qemu-aarch64 — le FIPS « abc » EXACT des DEUX lecteurs, le
  contrôle négatif divergent (t=179,90). Les consoles de ces runs
  vivent au dossier preuves-labo/ de ce kit. L'ÉMULATION PROUVE LA
  MÉCANIQUE, JAMAIS LE SILICIUM : aucun statut terrain n'en découle —
  le run Ampere A1 appartient au développeur.
