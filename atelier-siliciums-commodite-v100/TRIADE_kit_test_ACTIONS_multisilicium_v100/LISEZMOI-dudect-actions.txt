LE WORKFLOW : workflow/triade-siliciums-commodite.yml vit AUSSI au
dépôt (.github/workflows/triade-siliciums-commodite.yml — la copie au
workflow/ du paquet est la MÊME pièce pour le recoup). Il se déclenche
à la main (workflow_dispatch) ou au push qui touche l'atelier ; le

L'ÉTIQUETTE (dite d'abord, pour qu'aucune lecture ne naisse grandie) :
AUTOTEST-DISTANT — le silicium est RÉEL, le geste est celui du LABO.
Les runners sont MUTUALISÉS aux voisins inconnus (D206 : le t mesure
AUSSI eux) ; le DVFS sous l'hyperviseur est opaque ; sur macOS
l'affinité n'est pas posable (le t sera bruité, constaté) ; la
hiérarchie d'évidence est INCHANGÉE : le banc contrôlé (portable,
téléphone) demeure la référence ; ces runs sont des lectures de
commodité, JAMAIS le run terrain du développeur, JAMAIS des preuves.

LE PROTOCOLE ACTIONS-ARM-1 (l'équation pré-enregistrée du kit-D sur le
silicium serveur ARM64 — l'ÉGALATION du TELEPHONE-ARM-1, re-enregistrée
ici AVANT tout run) :
  Les CIBLES, dans cet ordre : eq-constant (contrôle positif — aucune
  divergence attendue), eq-branchue (contrôle négatif — DIVERGENCE
  attendue : la preuve que l'instrument détecte les fuites), 
  sha256-logiciel (aucune divergence attendue), sha256-arm-sha2 (VIT
  seulement si le noyau expose « sha2 » ET que le compilateur a accepté
  -march=armv8-a+sha2 — sinon REFUS NOMMÉ, le reste du run vit).
  Les CLASSES, deux par cible, ÉCHANTILLONS ENTRELACÉS : EGAL contre
  DIVERGENT (comparaisons), SECRET-FIXE contre SECRET-ALÉATOIRE
  (compressions).
  L'ÉQUATION : échauffement 100 paires par cible ; LOT=512 pour les
  comparaisons, LOT=4 pour les compressions ; N=60 puis N=200 puis
  N=400 DANS CET ORDRE ; le t de Welch sur les ticks, le seuil |t|>5.
  LE COMPTEUR : CNTVCT_EL0 (le compteur virtuel du SoC, « ticks »,
  jamais « cycles ») ; le repli CLOCK_MONOTONIC est NOMMÉ s'il vit.
  L'ÉPREUVE FIPS « abc » EXACT exigée avant toute mesure (fail-closed).

LE PROTOCOLE APPLE-ARM-1 (l'équation pré-enregistrée du kit-G sur
l'Apple Silicon — l'ÉGALATION du TELEPHONE-ARM-1, re-enregistrée ici
AVANT tout run) :
  Les CIBLES, dans cet ordre : eq-constant, eq-branchue,
  sha256-logiciel (les mêmes attentes), sha256-arm-sha2 (VIT si le
  compilateur expose +sha2 — sur Apple Silicon le défaut du clang
  d'Apple porte FEAT_SHA256 de facto — ET QUE L'ÉPREUVE FIPS l'accepte :
  sur macOS le canal noyau manque, l'épreuve décide seule, nommé).
  Les CLASSES, l'ÉQUATION, LE COMPTEUR, LE SEUIL, L'ÉPREUVE : les
  MÊMES que TELEPHONE-ARM-1 (LOT=512/4, N=60/200/400, Welch |t|>5,
  CNTVCT_EL0).
  LES ÉCARTS NOMMÉS du portage (jamais muets) : l'affinité REFUSÉE sur
  macOS ; l'identité au sysctl (machdep.cpu.brand_string, hw.model),
  pas au /proc ; le rapport médian logiciel/matériel, s'il vit, est LE
  CONSTAT DE CE SILICIUM (le téléphone a rendu 4,36 — CE silicium dira
  ce qu'il dit).

LA LECTURE HONNÊTE (à lire AVANT de s'inquiéter d'un verdict) :
  — |t| > 5 = dépendance AU SEUIL sur CET échantillon, CETTE machine
    mutualisée, consignée telle quelle ;
  — |t| <= 5 = aucune divergence au seuil sur cet échantillon — jamais
    « temps constant prouvé » ;
  — le contrôle négatif eq-branchue DOIT diverger (sinon l'instrument
    est CONTESTÉ — nommé) ;
  — les rapports médians (logiciel/SHA-NI, logiciel/FEAT_SHA256) sont
    LES CONSTATS DE CES SILICIUMS — jamais des cibles ;
  — un écart nommé est un RÉSULTAT aussi précieux qu'un vert (D189) :
    rapportez-le tel quel.
