Abstract
Large language model (LLM) agents currently produce native code by generating high-level source and
delegating to a compiler toolchain; the translation from intent to machine code passes through layers
the agent neither writes nor verifies. We report on TRIADE, a development protocol in which an LLM
agent writes native x86-64, RISC-V, and TLS 1.3 code directly as assembly notation, governed by signed
layer-I specifications, an encrypted and fragmented card binding intentions to byte ranges, and an epistemology separating oracle evidence (differential emulation in the laboratory) from terrain evidence
(execution on the developer’s real machine). A longitudinal single-case study validated the protocol
across eleven milestones (M0–M10, 26 October – 11 November 2026), delivering “Loupe”, a real Windows hex-editor written entirely under the protocol, then a pre-registered two-arm field campaign (D204,
12–16 November 2026; extension D210, 17–18 November) in which the same agent delivered every unit
twice over shared layer-I contracts — once as sealed hand notation (arm T), once as compiled C (arm
C) — closing green at both arms with every counted escape kit-side in the shared judge, the piece never
at fault, and the empirical attribution (the same compiled piece re-delivered through a minimal standard
kit) reading 14 VERT, 0 ROUGE. Four research questions are quantified on an append-only evidence
base (a 13,648-line engineering journal, a 13,988-line task log and a 4,814-line decision log, D1–D234):
(RQ1) the escaped-defect rate of changes that had passed every laboratory control — eleven of twelve
field iterations surfaced at least one escaped defect, each named to a class and a mechanism before
any fix, while the closing campaigns’ 29 witnessed deliveries produced zero escapes attributable to the
sealed notation itself; (RQ2) the measured token cost per validated change — under the adopted pointeronly localiser format a median of 1,103 tokens to locate a block (n=18, zero divergence, the response
a median 52 tokens), 3,374 to edit one and 3,674 to add one (the hunk-format campaign measuring the
edit at 2,452 with a 40-token response), against a naive whole-disassembly baseline of 300,304, with
the historical perimeters (M1, v0.14.0 content-only, v0.17.0 round-trip) explicitly labelled; (RQ3) the
defect classes structurally invisible to emulation — loader and PE-format semantics, ABI conventions,
harness assumptions — enumerated with their evidence, the unbound import leaf killing the compiled
arm’s field runs twice at the same slot; and (RQ4) hot-patch safety — zero post-patch regression across

Introduction

An LLM-based agent that develops software today almost always works at the level of high-level source
code, and the mapping from that source to machine code is delegated to a compiler toolchain. This division
of labour has an epistemological consequence: the agent’s intent is checked against source text, while the
bytes that execute are produced by a translation chain the agent does not write, does not see, and cannot
re-derive. Bugs in that mapping, and drift between what was specified and what was produced, become a
class of defects that no amount of source-level review can exclude.
TRIADE (Triple Mirror: Intention, Bytes, Card) is a protocol designed for the opposite position: the
agent writes native code directly, as assembly notation assembled by a deterministic, verifiable assembler
path — there is no optimizing or opaque translation chain; what the agent writes is, by construction, what
executes (assembly notation is verified by an exact round-trip against the emitted bytes at every build). The
protocol was developed and validated by a single human developer directing an LLM agent, over eleven
milestones between 26 October and 11 November 2026, and is documented in a 13,648-line append-only
engineering journal (Entrées consigned through 304; the campaign closures and the extension, Entrées 305–
357, carried in its 13,988-line companion task log and the campaign ledger journal at the archive), a 4,814line append-only decision log (D1–D234), and sealed artifacts whose SHA-256 fingerprints are consigned
at each sealing ceremony.
This paper is the first academic edition of that effort. Its purpose is not to argue that hand-written
machine code is superior to compiled code in general; it is to report, with the data the protocol itself produced,
what happens when an LLM agent develops real native software this way — what it costs, what breaks, what
laboratory verification could not see, and what governance was needed to keep the process falsifiable. The
protocol’s cryptographic and testing primitives (signature schemes, secret sharing, differential testing, key
ceremonies) are standard and cited; the contribution claimed is their integration into one agent-first pipeline,
together with the oracle/terrain epistemology and the signed-intent governance described below.

The study is structured around four research questions:
• RQ1 Escaped-defect rate. When a change passes every laboratory control (differential oracles, harnesses
at three fixed seeds, structural checks, seal guards), how often does it still fail on the real target machine,
and at what granularity can the failure be named?
• RQ2 Token cost per validated change. What does it cost, in LLM context tokens, to locate, edit, or add
a block of sealed native code under the protocol’s card-based indexing — measured end-to-end on the
final card, with distributions rather than single values?
• RQ3 Emulation-invisible defect classes. Which classes of defects are structurally invisible to a Unicornbased emulation harness, and therefore escape to the terrain regardless of laboratory coverage? Framed
differently: a compiler silently guarantees several of these classes — RQ3 quantifies what must be rederived, and learned, when the compiler is removed from the agent’s path.
• RQ4 Hot-patch safety. Can code be patched in place while sealed artifacts remain byte-stable, with zero
post-patch regression and an armed rollback barrier, across ISAs?
The remainder of the paper describes the protocol and the study methods (Section 2), the results per research question (Section 3), a discussion (Section 4), threats to validity (Section 5), related work (Section 6),
and declarations.

2

Methods

2.1

The TRIADE protocol in brief

TRIADE organises development in three indissociable layers. The intention layer (layer I) holds one normalized specification per code block: identifier, intent, pre/post-conditions and invariants, named failure
cases, verification vectors, fixtures, provenance and the decisions that shaped it. The block layer (layer B)
holds the assembly notation of each block, at fixed addresses, with deterministic assembly and a mandatory round-trip check (assemble, disassemble, re-assemble; any divergence refuses the build). The card
layer (layer C) is an encrypted, fragmented, signed index (the card) that binds every block to its byte range,
contract and fingerprints; only the card is needed to locate or edit a block, never the whole binary.
Eleven rules (R1–R11) fix the discipline; the load-bearing ones for this study are: R2 (written before
code: every block is specified before any notation byte exists); R4 (stable contract: a change may not
silently alter a block’s contract); R5 (verify then write: the agent must re-derive the check before writing);
R6 (crystallisation: an artifact may only be sealed after ten consecutive identical rebuilds); R7 (sealed inheritance: inherited bytes live at their sealed addresses, byte-identical); R10 (load-time verification: checksums
per block, signed version monotonicity, anti-rollback floor); R11 (no optimization without measurement).
The development loop itself (update an intention, re-derive the oracle, edit the notation, rebuild, verify,
seal) and the seal ceremony model are described in the protocol specification v0.15.6, which this edition
accompanies; we summarise only what the evaluation needs.
Governance: signed intent and append-only records. Every layer-I tree is condensed and signed with
an Ed25519 key kept strictly offline; a build refuses an unsigned layer I. Structural decisions are consigned
in an append-only decision log — each entry has an identifier, date, status, context, the retained choice,
rejected alternatives and amendment links; entries are never rewritten or back-dated. The fourteen signed
trees at the time of the study are verified by a guard that must pass before any build (14/14 at the last run).
Sealing a release is a fact of the card: the sealed tag lives in the card’s build fragment; the artifact’s bytes
never move (Table 5 lists the sealed artifacts and their fingerprints).
The oracle/terrain epistemology. The protocol distinguishes two evidence regimes. Oracle evidence is
produced in the laboratory: differential oracles derived from the layer-I specifications (never exported, always regenerated from I), scenario oracles that replay expected screens byte-for-byte, structural oracles that
read the composed image instruction by instruction, and Unicorn-based emulation harnesses with Windows

ABI shims. Terrain evidence is produced on the developer’s real machine: the sealed artifact, a scenarioloader script, and witnesses (byte-exact logs, showcase runs) that are pushed back to an evidence vault and

The agent. The developer directed an LLM agent (Z.ai GLM family, “the laboratory”) through short

ends with a consigned entry listing what was done, what was verified and what remains — plus the decision
log; these, with the evidence vault, are the primary sources of this paper. The agent is described here and in
the acknowledgements; it is not an author.

2.2

The validation programme and the case study

The protocol was validated by eleven milestones, each with measured exit criteria (Table 1); M0 established
the artifact chain, M2 hot patching on a real machine, M3 a million-case fuzzing campaign, M4 an encrypted
Schannel tunnel, M6/M7 portability to Linux and RISC-V, M8 direct syscalls, M9 pure TLS 1.3 (28 blocks,
official vectors from FIPS 180-4, RFC 2104/4231, RFC 5869, RFC 7748, SP 800-38D, handshake replayed
on the RFC 8448 transcript, and a real encrypted session with a real server), and M10 the full-scale test:
Loupe, a real Windows hex-editor application — 18 blocks in five families (file, digests, rendering, navigation, editing) — written entirely under the protocol, delivered as a field kit to the developer’s machine, and
run twelve times (Table 4). Verification volumes per milestone are consolidated in Table 3.

2.3

Measurements

Token budgets were measured three times under two documented perimeters. At M1 (decision D31/D34,
the generation-1 card): the single-shot content of each operation, cl100k_base. At v0.14.0 (D195): the
content alone re-measured on the Loupe-era material (the plan entry, the notation re-read and re-written,
the specification and notation written — n=10 per operation), the agent reasoning overhead estimated at
×1.08 from the era’s surgical revisions (an estimate, named as such, never confused with a measurement).
At v0.17.0 (the pre-registered plan ede70035…): the complete instrumented round-trip — the real prompt
(material verbatim plus request prose) and the real response, counted with the model’s native tokenizer as
read from the usage log of every call (the estimation abandoned), cl100k_base in parallel. The two remeasurements answer different questions (what the material costs to read, against what the full operation
costs to live through); the perimeters are documented wherever both values appear, and no direct crossperimeter comparison is drawn without the perimeter note. The M1 convention (D31/D34) was: tokens
to locate a block (read one frag-loc entry), to edit one (additional frag-con + notation), to add one
(additional profile thresholds). Escaped defects are counted per terrain iteration under an operational rule
defined once and applied uniformly: a run counts toward the escaped-defect rate if at least one defect that had
passed every laboratory control in force at the time was named (a class, a mechanism, an archived evidence
piece) before any fix — kit-side and piece-side defects both count, the deliverable being the kit+piece
ensemble; runs 6 and 7 each surfaced two such defects and each counts once in the run rate (the rate measures
escape incidence per delivery, not per defect); the run-7 [D54-QUATRIÈME] recurrence is counted as a
manifestation of the deposit-drift class first named in the M4-era campaign, not as a new class; and the
run-12 [T0-PÉRIMÉ] residue — a stale banner string touching no gate, disclosed in the run table — is not
counted: it violates no control’s contract and alters no behaviour any control guards, and counting a text
refresh as a functional escape would misstate the rate’s meaning. Hot-patch safety is measured as post-patch
regressions (target: zero) and as the byte-stability of sealed artifacts across patch campaigns. All numbers
reported in Section 3 are generated programmatically from the journal and decision log by the extraction
script shipped with this edition; the manuscript contains no hand-typed data value.

The D204 two-arm field campaign

The closing validation programme is a pre-registered comparison of the two ways of working on the same
contracts (decision D204, its plan hash-consigned before any measurement: a78caf8c…). Each campaign
unit is delivered twice, over one shared layer-I contract: arm T — the full TRIADE discipline (R1–R11:
the notation written by hand, the round-trip, the card, the oracles regenerated from I, the crystallisation, the
guard, the field kit) — and arm C — the standard compiled flow (the same contract read, the C source written,
gcc 14.2 -O2 cross-compiled for Windows, the tests as the standard flow practices them, the same field-kit
mechanism). The same agent, the same model family (glm-4-plus, the identifier reported by every logged
call), the same developer, the same real target machine: the arms differ only in the discipline. The plan fixes
four metrics: M1 (escaped defects per delivery, under the D202 rule and its named exclusions), M2 (real
tokens, read from the usage logs of every instrumented call — the ×1.08 estimation forbidden where a
log exists; a missing call is a named gap, never a reconstructed number), M3 (the developer’s human time
at the gesture, never recalled from memory), and M4 (verification compute time, monotone chronometer,
fixed command lists per arm). Directional, falsifiable hypotheses were registered before the first unit (H1
final health at both arms; H2 escaped defects within a factor of two; H3 the notation arm costlier in tokens;
H4-D204 longer human ceremonies for T; H5 verification time within one order of magnitude), with stop
rules: at most three deliveries per block, first green closes the unit, an app at most twelve deliveries, the
campaign stops at a red guard or a compromised piece.
The asymmetric delivery formats, and why. The two arms do not deliver the same binary format, and
the asymmetry is load-bearing for reading the escapes. Arm T’s piece is an EXE image composed at a fixed
slot of the sealed loupe.exe layout (the notation is assembled into the image the card already indexes;
the terrain kit maps it by sections and the scenario calls it at its address). Arm C’s piece is a DLL (gcc
-O2 -shared, one export per block declared in a .def file), because the standard flow’s unit of delivery
is a library the host loads: on the terrain the Windows loader binds the DLL’s import table (every leaf must
resolve), while the laboratory’s POSIX proof maps the image by sections and services the imports through
shims behind a SysV→msx64 trampoline. The loading paths differ exactly where the campaign’s escapes
live: the unbound-import-leaf class exists only on the DLL path (an EXE without that import has no leaf to
leave unbound), and it struck the compiled arm three times — twice at the same slot (the memcpy leaf, IAT
@+0x151a0: the scenario and then the host) and once at the memcmp leaf (loupe-13, IAT @+0x91a0). Table 7 reports the complete campaign — fourteen units (six controlled blocks and the application, each at both

3.3

RQ3: defect classes invisible to emulation

The eleven named classes of the Loupe campaign group into five families; each was invisible to the emulation harness for a structural reason, not a coverage gap — and each corresponds to a guarantee a compiler
normally provides silently (a loadable, relocatable image; ABI-conformant call sequences; conventional
error codes; runtime assumptions baked into the toolchain), which hand notation must re-derive explicitly,
one named lesson at a time:
1. Loader and image semantics (runs 1–3): an ASLR image without a relocation table (refusal 0xc000
007b); an image outside the proven envelope of eight prior artifacts (page hole, massive BSS); an uninitialized .data session frame (the initializer existed only in the harness’s ideal memory). The harness
parses images; it never loads them.
2. ABI conventions with hardware consequences (run 4): msx64 stack arguments 5+ written at the home
space instead of [rsp+0x20]+, and stack misalignment at call sites (rsp ≡ 8 mod 16) — harmless
under emulation, fatal with a real SSE-using gdi32. This class gave birth to a static msx64 ABI audit
at build time, which then caught two further alignment defects no one had seen.
3. Operating-system loader behaviour (runs 5, 9, 11): Windows refusing a write-open on the file of a
live mapped section (gle 32); import tables walked by the loader at DWORD stride while the build wrote
QWORD entries — the first cause of all six showcase deaths, found on the artifact’s bytes; and the structural
false negative that a library loader never resolves an EXE’s imports (the “liaison” probe could never
succeed as designed — the showcase itself is the proof).
4. Error-code conventions (runs 6–7): an hInstance read from the PEB instead of GetModuleHandleW
(NULL); negative return codes read as unsigned 32-bit values by the kit while the piece delivered them
sign-extended.
5. Harness- and kit-embedded assumptions (runs 8, 10 and the pre-run fix of run 11): a probe killed by its
own unguarded Python; a 64-bit HMODULE truncated by ctypes to a C int because argtypes was not
set; a bare ret neutralizing an entry point whose return value the loader reads in DllMain semantics.
These are defects of the test rig, named with the same discipline as defects of the artifact.
The pattern across families: the emulator verifies logic well and environment not at all. The protocol’s
answer is asymmetric — add the static audits that can see the environment-sensitive classes (ABI, image
format), and route the rest through terrain evidence with named-defect accounting, rather than pretending
the harness can be completed.

Discussion

What the data supports. A single developer with an LLM agent delivered, in 17 days, a cross-platform
native codebase with a pure TLS 1.3 stack and a real Windows application, under a discipline that made
every claim checkable: every defect named, every fix diffed, every seal fingerprinted, every decision append-

TRIADE — academic edition v0.20.0

24

only. The escaped-defect data (RQ1/RQ3) is, to our knowledge, the first quantified account of where agentwritten native code fails when laboratory verification is strong but environmental fidelity is absent: not in
logic, but in loader semantics, ABI conventions and rig assumptions. Agent-failure quantification exists
at source level in repository-scale settings [1], and the verified-compilation line quantifies the translator’s
own guarantees [2]; the claim is scoped to what is new here — the sealed-notation level, under signed-intent
governance.
What the data does not support. The study cannot claim that the protocol is more productive or more
correct than a compiler-based workflow: one case, one agent family, one developer — though the D204
campaign now provides the two-arm comparison on fourteen units (behaviourally equivalent at the contracts; the cost and verification-time pairs still n=1 each). The token budgets were measured three times —
M1 single-shot, the v0.14.0 content-only re-measurement, the v0.17.0 instrumented round-trip (the perimeters documented; never compared without the note) — and the campaign adds the only fully instrumented
head-to-head unit. The oracle is derived from the same layer I it checks, so specification errors are shared,
not caught — mitigated, not removed, by the second, isolated agent that regenerated the crypto constants
with zero divergences (v0.14.0; cross-family independence remains the named gap). Memory safety is enforced only to the depth of the ABI audits and the fuzzing campaigns; constant-time is verified structurally
(secret-independent instruction traces in emulation) and its real-hardware dudect timing is measured and
signed (the runs of 13 November 2026, Section 3.7; Tables 6 and 9) — cache-timing and power side channels remain unmeasured. These limits are stated, not smoothed over; the companion programmes of the
two subsequent editions addressed several of them directly (mutation testing, bounded memory safety and
structural constant-time in v0.11.0; the formal model of the vault chain in v0.12.0), and the benchmark audit
of the present edition is itself an instance of the method applied to its own claims.
On the “no compiler” position. We phrase the protocol’s position precisely: TRIADE eliminates the optimizing and opaque translation chain by having the agent write the assembly notation itself, with a round-trip
check making the notation WYSIWYG (what-you-write-is-what-executes) at every build. It does not eliminate the assembler, the operating system, or the platform ABI — those are called through their documented
conventions, like any native binary. Similarly, the sovereignty programme’s claim about expropriation is
narrow: the evolution of stolen code is blocked (signed layer-I intent, sealed inheritance, offline keys, deadman’s-switch Shamir escrow); the execution of a stolen copy is not, and the specification says so.

A bounded formal model of the CF3 vault. The sealed-vault chain (CF3: three-element lock, two-act

• P1 (secret below threshold). With ≤ 2 of the three elements, the adversary never reaches the learnedsecret state: proved in the model (0 counterexamples). The KEK derivation binds all three elements

monotonicity, mechanically re-checked over every transition).
• P3 (no destruction on wrong passphrase). Wrong-passphrase attempts lead only to the benign retry

proved in the model (0 counterexamples).

Threat model restructured in two planes. The single threat table of the specification is restructured along
the protocol’s own founding distinction — obfuscation protects intellectual property, hardening protects
execution — into two planes:
• Plane IP (intellectual property). Reverse engineering (time bought, eroding with LLM decompilers),
expropriation (the evolution of stolen code is blocked — signed layer-I intent, sealed inheritance, offline
keys, Shamir dead-man’s switch — its execution is not), redistribution (per-build fingerprints, canary
trap). Confidentiality of the card dominates; loss of confidentiality is remediable (rotation, variants).
• Plane execution safety. Card poisoning/corruption (signature, cross-lock, AEAD), evil-maid on container or trap media (epoch cross-checks, AEAD tags, the undervivable verif field), container-plustrap rollback (three epoch witnesses), altered binary (per-block checksums, signed manifest at load),
non-conforming environment (profile checks, fail-closed), agent failure (R2/R5, oracle from I, budgets).
Integrity and availability dominate; destruction is survivable (CF2 fragments, the trap media).

Threats to validity

Internal. The oracle is circular with respect to layer I (both derive from the same specifications); a specification error passes the oracle by construction — the v0.11.0 independence runs (distinct derivation routes,
system generator, spec↔harness ↔hashlib tripartite confrontation) found zero divergences, and the v0.14.0
programme closed the remaining agent gap at same-family level: an isolated second agent instance regenerated the MD5/SHA-256 tables from the mathematical definitions alone with zero divergences across the
128 constants; true cross-family independence remains the named gap. The crystallisation rule (ten identical rebuilds) checks determinism, not correctness. The mutation-testing survivors (56/832 after the v0.14.0
composition re-run; 138/832 at v0.11.0, concentrated in orchestration/UI blocks without an isolated-mutant
semantic killer) are a named, measured gap — and the v0.13.0 audit of our own v0.11.0 benchmark, which
caught a perimeter artifact that inflated a claim fifteen-fold, is itself evidence of this threat class: instrument
defects contaminate results symmetrically, and were caught here only because the edition required the audit.
External. N=1: one project, one developer, one agent family; the compiled-reference comparison of v0.14.0
exists but shares the laboratory harness and a single seed; independent replication (a second developer, a
second domain) remains future work. Construct. The escaped-defect count depends on what counts as a
“named” class — we counted conservatively (a class is counted once even if it killed several runs); the token
budgets of M1 and v0.14.0 measure content reads (the latter on the final Loupe-era card, the reasoning estimated and named), the v0.17.0 re-measurement covers the full instrumented round-trip on the same card,
and the two perimeters are never compared without the note — cross-perimeter ratios are meaningless by
construction. Construct, campaign-specific: the shared kit and the asymmetric formats. The D204 campaign shares its terrain kit between arms while delivering different formats (an EXE image at a fixed slot
for T, a DLL bound by the Windows loader for C), so the delivery metric mixes arm-neutral rig defects with
format-specific ones. The sensitivity analysis, per escape: of the six counted escapes, three are arm-neutral
rig classes (a harness constructor, the launcher prose, the console codec — a standard flow’s test rig can
carry exactly these), and three are manifestations of the single unbound-import-leaf class, which exists only
on the DLL path (an EXE without that import cannot leave the leaf unbound) — a compiled-flow-specific
escape, not a notation-versus-compiler difference. The empirical attribution test was run at the extension’s

Related work

Positioning (requalified in the present edition). The novelty of TRIADE is not the generation of assembly by an LLM — assembly generation and compiler-style search have been quantified before: STOKE [3]
formulates loop-free binary superoptimization as stochastic search; SuperCoder [4] is the strongest published LLM result on improving already compiled assembly (95.0% test-pass correctness and a 1.46× average speedup over gcc -O3 after task-specific fine-tuning — superoptimization, a distinct problem from
governance); the LaaC/CompilerEval line [5] measures end-to-end compilation from source code to assembly by LLMs (feasible but with low success rates — the compiler’s job, attempted whole); and Nova [6]
builds generative language models for assembly code (hierarchical attention, contrastive learning, strong
decompilation and similarity results). What no prior account quantifies is the governance: signed-intent
layer-I contracts sealed by a human hand, append-only journals (engineering, task, decision) as the sole
data source, every escaped defect named to a class and a mechanism before any fix, and a pre-registered
two-arm field campaign comparing the disciplined and the standard workflows on the same contracts at a
real machine — with the oracle/terrain epistemology that a laboratory harness is structurally blind to the
classes that only loading, linking and hardware reveal.
Design by contract and specification-first development. TRIADE’s layer I applies design-by-contract
ideas [7] at the machine-code level: one specification per block, pre/post-conditions, named failure cases.
The novelty is not the contract style but the binding of contracts to byte ranges through the signed card, and
the rule that no notation byte exists before its specification.
N-version and property-based testing. The differential oracles and scenario oracles follow the propertybased testing tradition [8] and the classic redundancy arguments of N-version programming [9]: independent
instruments (three concurrent harnesses, oracles regenerated from I, never exported) must agree. TRIADE
extends the independence requirement to the terrain (a machine the laboratory never controls) and to the
rig itself (kit defects are named with the same discipline as artifact defects).
Certification discipline. The milestone/exit-criteria structure and the append-only, amend-or-invalidate
decision log borrow from airworthiness process standards such as DO-178C [10]: objectives with independence, traceability, and configuration control — here applied to agent-written native code, with every
criterion measured rather than attested.
Supply-chain integrity. Per-build fingerprints, signed manifests, sealed tags and key ceremonies align
TRIADE with reproducible builds [11], in-toto’s layout attestations [12], SLSA’s build levels [13], survivablekey-compromise update systems (TUF) [14] and automated signing at scale (Sigstore) [15]; the offline rootkey ceremony follows the discipline of DNSSEC key ceremonies [16]. TRIADE’s addition is applying these
controls to fragments of a development state (the card) rather than to released artifacts only, and making the
sealed tag a fact of the card while the artifact’s bytes stay frozen. Secret sharing of the master key [17] is
used both for escrow and for the dead-man’s switch.

TRIADE — academic edition v0.20.0

29

Live patching. Hot patching of native code has a long lineage, from dynamic software updating [18]
and general-purpose DSU systems such as Kitsune [19] and POLUS [20] to industrial kpatch-style trampolines [21]. TRIADE’s contribution is the governance wrapper: a patch is a surgical, diffed, card-tracked
revision of blocks at stable addresses, with crystallisation, rollback and cross-ISA rules (x86-64 trampoline
vs. RISC-V scratch+fence.i), validated by oracle replay and, since M9, requiring a terrain run recouped
on pieces before any seal.
Repository-scale context for LLM agents. The token-budget programme (fragmented card, one fragment per operation, no full-binary reads) addresses the measured context limits of LLM agents: performance
degradation in long contexts [22] and the need for repository-scale retrieval and navigation [23, 24]. The
card is, in effect, a signed repo-map for machine code: a compact index that lets an agent operate on a large
binary without ever loading it.
Learned and verified compilation. The compiler side of the argument has moved in two directions:
learned optimisation, with LLM-based compiler foundation models trained on optimisation traces [25], and
verified compilation, where the translator is not removed but proven, as in CompCert [2]. TRIADE takes
the opposite door: instead of making the compiler smarter or proving it correct end to end, it removes the
optimising translator from the agent’s path and re-derives its guarantees explicitly — the WYSIWYG roundtrip at every build, at a measured token cost. The comparison is not adversarial: CompCert answers “can
the translation be trusted?”, TRIADE answers “what does the agent learn when it must write, and therefore
own, the bytes?”
Agent-driven software engineering. SWE-agent [1] quantifies what interface design does for repositorylevel agent performance — at source-code level, in hosted repositories. The RQ data of the present study
is the sealed-notation counterpart: what breaks when the same class of agent operates on native code under
signed-intent governance. The two layers are complementary; to our knowledge no quantified account
exists between them.
Simulation-to-reality transfer. The oracle/terrain epistemology is a deliberate instance of the reality-gap
tradition: evolutionary robotics learned that controllers evolved in simulation fail on real hardware unless
the gap is itself modelled [26]; modern sim-to-real work randomises the simulator to close the gap [27],
and hardware-in-the-loop validation interposes real components between the two [28]. TRIADE’s answer
is asymmetric: it does not attempt to close the gap by improving the emulator, but makes the gap itself the
measured object — every escape is a named, falsified class with an archived evidence piece (RQ1), and the
RQ3 taxonomy is the resulting map of the gap.
Positioning. None of the cited primitives is novel. The claimed contribution is the integration — contractfirst notation at the byte level, signed-intent governance, oracle/terrain epistemology with named-defect
accounting — evaluated end-to-end by building a real application with an LLM agent and reporting where
it failed.

Conclusion

We reported the first academic edition of TRIADE, a protocol under which an LLM agent writes native code
by hand under signed-intent governance, and a longitudinal single-case evaluation of its eleven-milestone
validation programme. The data, drawn entirely from the protocol’s own append-only records, quantifies
the cost (medians of 1,277/3,374/ 3,674 tokens per locate/edit/add at the instrumented-round-trip perimeter; the content-only and M1 values remain labelled history), the escape dynamics (eleven named defect
classes over twelve field iterations, all environmental; the closing campaign’s 22 deliveries adding zero
notation-side escapes and six kit-side ones, every one reconciled and attributed), and the patch safety (zero
post-patch regression, armed anti-rollback) of the approach. The Loupe application — a real Windows hex
editor born entirely from the method, sealed twice, and alive on its user’s machine — is the existence proof
that the pipeline can carry a real deliverable. The second edition strengthened the evidence: 83.4% mutation kill with the cryptographic families at 100%, zero-crash coverage-guided fuzzing of the untrusted-input
